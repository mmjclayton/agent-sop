## Summary

Adds `scripts/refresh-priorities.sh` (new, 109 lines): parses `Backlog.md` for `### P<n>` headings followed by a backticked status line and splices `[OPEN]`/`[IN PROGRESS]`/`[BLOCKED]` items into a `<!-- priority-items:start -->`/`<!-- priority-items:end -->` sentinel block in `CLAUDE.md`, replacing a hand-maintained list. Wires it into `/update-sop` Step 3, and updates both `CLAUDE.md` templates and `docs/sop/claude-agent-sop.md`'s structure spec to describe the section as derived. Reproduced the parser against a copy of this repo's own `Backlog.md` in a scratchpad and it correctly extracted all 13 live `OPEN` items with none missing or spurious — the happy path works. But the parser tracks "current heading" and "current status" independently by line proximity rather than by structural association, and that assumption breaks silently, not loudly, in several reachable cases below.

Severity: CRITICAL

## Findings

- `scripts/refresh-priorities.sh:95-107` (awk splice) — if the end sentinel is missing, mistyped, or reordered ahead of the start sentinel, everything in `CLAUDE.md` after the broken marker is silently deleted, with exit 0 and a `Priority items refreshed: CLAUDE.md` success message. Reproduced: seeded a `CLAUDE.md` with `<!-- priority-items:start -->` / `<!-- priority-items:ends -->` (typo — trailing `s`) followed by `## IMPORTANT SECTION THAT MUST SURVIVE\nThis content must not be deleted.`; after running the script that section was gone from the output entirely, replaced by nothing. The awk state machine sets `skip=1` on the start marker and only clears it on an exact-match end marker (`:102`); with no matching end marker downstream, `skip` never resets and every remaining line in the file is dropped (`:106`, `!skip { print }`). This is silent, unbounded content loss in the one file `CLAUDE.md` calls "single source of truth"-adjacent, gated only by exit 0, and directly contradicts this repo's own Rule 2 ("never delete without a trace") — the rule cited as P92's own motivation for not just deleting the hand-written section outright.
  Fix: before writing, verify the file contains exactly one occurrence of each sentinel and that start precedes end (`grep -c` both, compare counts and positions); abort with a non-zero exit and no write on mismatch.

- `scripts/refresh-priorities.sh:74-86` (status-line matching) — the parser does not require the status line to *immediately* follow its heading; it consumes the first `` `[...` ``-prefixed line seen after a heading and then clears `pending_heading` regardless of whether that line's bracket content matched a real status (`:85`, unconditional after the inner `case`). If any body line between a heading and its true status tag itself starts with a backtick + bracket — a quoted reference, a pasted tag example, anything — that line is consumed as "the" status, the real status line further down is treated as ordinary text (`:75` silently `continue`s once `pending_heading` is empty), and the item vanishes from the derived block with **no error and no items-found signal to distinguish it from a legitimately closed item**. Reproduced with a single-item Backlog containing one genuinely `[OPEN]` item whose heading is followed by a body line starting with `` `[Reference]` `` before its real `` `[OPEN] [Bug]` `` tag: the derived block rendered `*No open items. Everything in \`backlog4.md\` is shipped, deferred, or closed.*` — a false statement presented as the successful, refreshed output for a backlog that has exactly one open item. This is the fail-open case flagged as the worst defect class for this feature, and it requires no malformed input, only an ordinary body sentence that happens to open with a bracketed reference.
  Fix: require the status line to be the very next non-blank line after the heading (track line-adjacency, not just "seen since"), and treat a heading with no adjacent status match as a parse error worth surfacing (stderr warning at minimum), not a silent skip.

- `scripts/refresh-priorities.sh:69-87` (no fence-awareness) — the loop has no concept of fenced code blocks, so a `### P<n>` heading and `` `[...] `` status line pasted as an illustrative example inside another item's body — e.g. a bug reproduction showing sample Backlog markdown — is parsed as a real, independent item and injected into `CLAUDE.md`. Reproduced: a `[SHIPPED]` item whose body contains a fenced snippet quoting ` ```\n### P99 — Fake injected item\n`[OPEN] [Feature]`\n``` ` (illustrative, explicitly captioned "just illustrative markdown pasted into the postmortem") produced `- P99 — Fake injected item — [OPEN] [Feature]` in the derived output, ahead of the real next item. This Backlog.md already contains a fenced block of exactly this shape (P73's bash reproduction, `Backlog.md:1467-1471`) and the file's own style regularly pastes example markdown/output into findings (e.g. P82's `awk: newline in string ### P1\n10\n11\n...` at `Backlog.md:1686`) — a heading-shaped string inside a fence or inline example is a realistic future entry, not a contrived edge case.
  Fix: track fence state (toggle on lines matching ` ``` ` or `~~~`) and skip heading/status matching while inside a fence.

- `scripts/refresh-priorities.sh:67,90` (fail-open with no structural sanity check) — the script hardcodes the heading depth at `### P` (`:70`). If a Backlog.md uses a different heading depth (e.g. `## P<n>`, which is a plausible drift if a project's Backlog is reformatted or a non-default template variant is used), zero headings match, `FOUND` stays `0`, and the output is the same `*No open items...*` message as a real all-shipped backlog — exit 0, no warning. Reproduced with a single genuinely-open item under an `## P70` (two-`#`) heading; output was `*No open items. Everything in \`backlog5.md\` is shipped, deferred, or closed.*`. There is no check that distinguishes "0 headings found at all" (probable structural mismatch) from "N headings found, all terminal status" (legitimate). The current templates (`docs/templates/backlog-template.md:32`) do standardise on `### P`, which limits blast radius today, but the script itself has no defence if that convention drifts.
  Fix: count `### P` headings found (`heading_count`) separately from `FOUND`; if `heading_count == 0`, treat it as a parse failure (non-zero exit, stderr message) rather than a legitimate empty state.

- No automated fixture coverage for `scripts/refresh-priorities.sh`. `CLAUDE.md:85-86` names `docs/benchmark/*-fixtures/run-tests.sh` as this repo's test convention for scripts of this class ("Run them when touching the validator or the migration script"), and the pattern this script explicitly imitates (`scripts/refresh-rollup.sh`) was itself the subject of a fixture-discoverable bug fixed in `docs/reviews/2026-08-03_solo_P84.md`. The four defects above (data-loss splice, proximity misattribution, fence-blindness, heading-depth fail-open) are all fixture-shaped — before/after pairs with an expected derived block — and none is codified as a regression test. The commit message's "Tested:" paragraph describes ad hoc manual runs, not a checked-in suite.
  Fix: add a `docs/benchmark/priority-fixtures/` (or equivalent) harness with at least: happy path, no-sentinel opt-out, missing/malformed end sentinel, non-adjacent status line, fenced-block example, and non-`###` heading depth.

- `scripts/refresh-priorities.sh:57-61` and the commit message both claim "`|| true` on the grep... the exact class P84 fixed" and "the grep is guarded" — there is no `grep` anywhere in the extraction path (`:67-88` is a `case`/`while read` loop, not a `grep` pipeline). The script does correctly avoid the P84 class of bug, but for a different reason than the one documented: there's no pipe to fail under `pipefail` in the first place. The stale comment/commit claim describes a guard that doesn't exist in the code it's attached to, which will mislead whoever next edits this script looking for the "grep" to preserve.
  Fix: correct the comment at `:57-61` to describe the actual mechanism (a plain `case` loop has no command whose failure `pipefail`/`errexit` can propagate), and correct the claim in future commit messages referencing this script.

- `CLAUDE.md:43` vs this commit — the motivating case in the commit message ("agent-sop's own copy drifted inside this session ... still read 'only decision-blocked items remain' after P83-P86 shipped") is not fixed by this commit. `CLAUDE.md` is not in the diff (`git show 7138852 --stat`), still carries the old `## Current Priority Items (as of 2026-08-03)` heading with a hand-written list, and has no sentinel block — so `scripts/refresh-priorities.sh` would hit its opt-in skip path (`:49-52`) if run against it today. `setup.sh`'s `copy_project_file` (P86) never overwrites an existing `CLAUDE.md` even with `--force`, so `setup.sh` cannot retrofit the sentinel either. Neither the diff nor `/update-sop` Step 3's new instructions (`.claude/commands/update-sop.md:259-270`) describe a one-time migration step for converting an existing hand-written section into the sentinel form. The specific drift instance the commit opens with citing as evidence remains live and unaddressed after this commit merges.
  Fix: either migrate this repo's own `CLAUDE.md` to the sentinel form in this change or a fast-follow, or add an explicit migration note to Step 3 / the SOP structure spec for existing projects.
