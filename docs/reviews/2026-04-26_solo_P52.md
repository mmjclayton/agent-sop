## Findings

- `docs/sop/harness-configuration.md:203–205` — The idempotent jq merge example references `scripts/learnings-hook.sh`, which explicitly does not exist. The decision file and Backlog P52 both state this is doc-only with no runtime script. A consumer copying the jq snippet verbatim gets a settings.json entry that calls a non-existent script — the hook silently fails on every fire. Fix: replace `"scripts/learnings-hook.sh"` in the jq snippet with the actual inline `echo` command from the main JSON block above it, or add a note that the placeholder must be replaced with the consumer's own script path before the snippet is usable.

- `docs/sop/harness-configuration.md:196` — "Stop stdout injects into the next user turn" is imprecise and may be incorrect for a strict "last turn" session. Stop fires after every agent response; if the session genuinely ends without a subsequent user turn (e.g. user closes the window, automated pipeline exits), the stdout never reaches the context. The claim is effectively "stdout injects if there is a next user turn", which the decision file (line 30) states correctly: "sessions that never get a next user turn lose the prompt." The harness-configuration prose omits this qualifier. A consumer who reads only the harness doc may over-estimate the reliability of Stop stdout for the session-end case. Fix: add the qualifier inline — e.g. "Stop stdout enters the next user turn, if one occurs; sessions that end without a subsequent turn will not see the prompt (the `/update-sop` Step 5 sub-step is the safety net for this case)."

- `docs/sop/harness-configuration.md:196` — The `stop_hook_active` guard claim reads: "block-decision forces an extra turn and requires a `stop_hook_active` guard against infinite loop." `stop_hook_active` is a Claude Code environment variable set to `1` when a Stop hook is running, used to prevent a Stop hook from triggering another Stop cycle. The claim is accurate for a Stop hook that invokes the Claude agent recursively. For a simple `decision: block` returning text, no recursive loop occurs — the extra turn is the concern, not a loop per se. The wording conflates two separate issues (extra turn vs infinite loop guard). Fix: split into two sentences: "Block-decision at Stop forces an extra tool-use turn after the user has signalled done. If that turn itself triggers Stop, a loop is possible — hence `stop_hook_active` exists. stdout avoids both."
