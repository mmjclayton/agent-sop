## Summary

Adds `scripts/resolve-resume-path.sh` (174 lines) as the single derivation for the machine-local `project_resume_<agent-id>.md` path, and rewires the three existing implementations — `/update-sop` Step 7 (write), `/restart-sop` Step 0d + Step 2 (read), and `scripts/validate-state-transitions.sh --check-drift` (read) — to call it instead of inlining the logic. Removes the write-side legacy-`project_resume.md` fallback (kept read-only), fixes three collateral over-broad-lookup instances (`sop-checker.md` substring match, the SessionStart hook's `~/.claude/projects/*/memory/` glob, `/restart-sop`'s sibling-agent glob), and adds a 13-case fixture suite at `docs/benchmark/resume-path-fixtures/run-tests.sh`. I ran all four fixture suites in the repo (`resume-path` 13/13, `state-transition` 20/20, `drift` 5/5, `priorities` 8/8) and they all pass with no regression from the `--check-drift` rewrite.

I independently verified the core correctness claim: `bash scripts/resolve-resume-path.sh --dir` on this machine returns `/Users/matt_clayton/.claude/projects/-Users-matt-clayton-Projects-agent-sop/memory`, byte-identical to the value `CLAUDE.md:116` has hardcoded as this project's real memory directory. The `sed` hash pipeline in `resolve-resume-path.sh:136` is character-for-character identical to the one removed from both `restart-sop.md` and `validate-state-transitions.sh` in this same diff. I also drove `--check-drift` through both graceful-degrade paths directly (outside any git repo, and with `HOME` pointed at a fake git-repo root) and confirmed it exits 0 with a stdout message in both cases — the P73 class of bug (silent non-zero exit, empty stdout and stderr) does not reproduce here.

Two gaps keep this out of clean APPROVE: a write-side instruction two steps below the one this PR just fixed still carries the exact same unresolved-placeholder defect, and the new fixture suite's "13 cases" leaves the one platform/hash-dependent branch of the resolver completely unexercised.

Severity: HIGH

## Findings

- `.claude/commands/update-sop.md:553` (Step 9 — Update MEMORY.md index) still reads: "add them to `` `~/.claude/projects/[project-hash]/memory/MEMORY.md` ``" — the identical unresolved-placeholder defect P96 exists to fix, 79 lines below Step 7's own fix in the same file, same commit. An agent following Step 9 literally still writes MEMORY.md into whichever memory directory the *session* happens to own — the exact P96 failure mode, for the memory index instead of the resume file. The read/audit side of this diff already generalized to MEMORY.md correctly: `.claude/agents/sop-checker.md:45` now says "For local files (project_resume.md, MEMORY.md), resolve the memory directory with `bash scripts/resolve-resume-path.sh --dir`". Step 9 is the write side of that same file pair and was not updated to match — this is the write/read asymmetry P96 is named for, reintroduced one file down. The same unfixed instance recurs at `docs/examples/existing-project-migration.md:184` ("Ensure it exists at `` `~/.claude/projects/[project-hash]/memory/MEMORY.md` ``"), in the identical file whose neighbouring `project_resume` checklist line (`:281`) this diff *did* fix to `` `bash scripts/resolve-resume-path.sh --dir` ``.
  Fix: change Step 9 to `MEM_DIR=$(bash scripts/resolve-resume-path.sh --dir) || exit 1` then append to `"$MEM_DIR/MEMORY.md"`, and update `existing-project-migration.md:184` to the same pattern used at `:281`.

- `docs/benchmark/resume-path-fixtures/run-tests.sh` has no case for the hash-derived agent-id branch at `scripts/resolve-resume-path.sh:117-121` (the `shasum -a 256 | cut -c1-6` / `sha256sum` fallback, which fires when `git worktree list` reports more than one worktree and neither `CLAUDE_AGENT_ID` nor `.sop-agent-id` is set). All 13 cases resolve agent-id via the `CLAUDE_AGENT_ID` env override, the `.sop-agent-id`-file override, or the `count<=1` "solo" default (`run()` never calls `git worktree add`) — every one short-circuits before line 117. That branch is also the one place `resolve-resume-path.sh`'s `resolve_agent_id()` provably differs from the two inline copies of the same function that the diff leaves untouched: `resolve-resume-path.sh:112` treats an empty string *or* `"0"` `git worktree list` count as `solo` (`[ -z "$count" ] || [ "$count" = "0" ] || [ "$count" = "1" ]`), while `restart-sop.md:64` and `update-sop.md:37` treat only literal `"1"` as `solo` (`if [ "$count" = "1" ]`) and fall through to the hash branch on an empty or `"0"` count. "13 passed, 0 failed" reads as full coverage of the precedence chain described in the script's own header comment; the one part of that chain that's platform-dependent (`shasum` vs `sha256sum`) and truncation-prone (`cut -c1-6`) is the part nothing in the repo exercises — I confirmed this with `grep -rn "worktree add\|shasum\|sha256sum" docs/benchmark/*/run-tests.sh`, which returns nothing across all four suites.
  Fix: add a case that does `git -C "$PROJ_A" worktree add "$TMP/wt2" -b wt2-branch`, clears `CLAUDE_AGENT_ID`/`.sop-agent-id`, and asserts the resolver's `--agent-id` output matches a hand-computed `shasum -a 256 "$PROJ_A" | cut -c1-6` (or the `sha256sum` equivalent).

- `scripts/validate-state-transitions.sh:513-514` re-emits the resolver's captured stderr only when `[ "$resolver_status" = "0" ]`. When the resolver instead fails with status 1 for the "not a git repository" reason (as opposed to "in a repo, no resume file yet" — both currently collapse to the same status 1), that more specific message — `"resolve-resume-path: not a git repository — cannot derive a project-scoped memory directory."`, written to `$resolver_err` — is captured and then discarded by `rm -f "$resolver_err"` at `:522` without ever reaching the operator. I reproduced this directly: running `--check-drift` from a plain non-repo directory prints only `"check-drift: no project_resume file found — skipping (first session, or fresh repo)"`, which is a plausible-but-wrong explanation for a directory that was never a git repository at all. D1's exit-code contract still holds — I verified `--check-drift` exits 0 with non-empty stdout in both the non-repo case and the home-root-refused case (`resolver_status=2`) — so this is a diagnostic-fidelity regression, not a correctness break.
  Fix: either give `resolve-resume-path.sh` a third exit status distinguishing "not a repo" from "no resume file yet," or have the validator re-emit `$resolver_err` on any status other than 2 (not only on status 0).

- `Backlog.md`'s P96 entry ("Also open (not fixed here)" paragraph) is inaccurate on the count it uses to justify deferring the fix: it says agent-id resolution is "still implemented three times — `/update-sop` Step 0, `/restart-sop` Step 0, and `scripts/validate-state-transitions.sh` — and `resolve-resume-path.sh` now adds a fourth." `scripts/validate-state-transitions.sh` no longer has an inline agent-id derivation at all after this diff — `grep -n "agent_id" scripts/validate-state-transitions.sh` (case-insensitive) returns only a comment referencing the concept, confirming this diff removed that copy rather than leaving it as a third independent implementation. The correct count is two pre-existing copies (`restart-sop.md:48-76`, `update-sop.md:21-49`) plus the new one in `resolve-resume-path.sh:99-122` — three, not four. The same paragraph's "All four share the same precedence chain... so they agree today" doesn't hold at the edge either, per the finding two above: an empty/`"0"` `git worktree list` count is exactly the scenario the removed code's own comment (visible in this diff's deletion at old `validate-state-transitions.sh:474-482`) called out as a real off-git failure mode, and the surfaces disagree on it.
  Fix: correct the Backlog paragraph to the actual post-diff count and drop or qualify the "agree today" claim.
